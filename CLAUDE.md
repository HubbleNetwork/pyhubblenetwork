# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

pyhubblenetwork is a Python SDK for communicating with Hubble Network IoT devices over Bluetooth Low Energy (BLE) and securely relaying data to the Hubble Cloud. It provides both a programmatic API and a CLI tool.

## Commands

```bash
pip install -e '.[dev]'
```

## Architecture

### Package Structure
The SDK uses a src layout with the main package at `src/hubblenetwork/`. Public API is exposed through `__init__.py` - import from the package top-level.

### Core Modules

- **`org.py`** - `Organization` class: credential-scoped operations (register devices, retrieve packets, list devices). Automatically resolves environment (PROD/TESTING) from credentials. `iter_devices()` and `iter_packets()` are generators that handle pagination without accumulating, each accepting an `on_page(page, total_so_far)` callback for progress; `list_devices()` and `retrieve_packets()` are `list()` wrappers over them and keep returning lists. `decode_packets(packets)` has the cloud decrypt any number of `EncryptedPacket`/`AesEaxPacket` (no key needed): it dedupes identical advertisements, sends batches of 25, and returns `list[DecryptedPacket | None]` aligned to the input (`None` = the cloud couldn't decrypt it for this org; results matched to inputs by the echoed `advertisement.payload`). Other packet types raise `ValueError`. Packets outside the endpoint's window (>72h old, >2h future) or with empty bytes are answered `None` locally, because one invalid item makes the endpoint 400 the whole batch. The module-level `org.decode_packets(credentials=, env=, packets=)` is the same thing for a caller that already resolved the environment (`ble validate` uses it, since constructing an `Organization` costs two requests). `get_device(id)` fetches one device (`NotFoundError` if absent). `ingest_packet(packet)` is the original async ingest path (unchanged). The decode endpoint also stores what it decodes, so never both ingest and decode the same packet.

- **`cloud.py`** - Low-level HTTP client for Hubble Cloud API. Contains `Credentials`, `Environment` dataclasses and all REST endpoint functions. Uses `httpx` for HTTP requests. `decode_packets(credentials, env, advertisements, metadata=None)` is one `POST /org/{id}/packets/decode` call (1..`DECODE_BATCH_LIMIT`=25 wire-format dicts built by `packet_to_advertisement()`; `rssi` must be an int and `location` is required, so `None` becomes a 0,0 placeholder). A 403 is re-raised as `PermissionDeniedError` naming the `read-packets` scope. `advertisement_bytes()` returns the exact service-data bytes the cloud needs.

- **`ble.py`** - BLE scanning for beacon packets (UUID 0xFCA6). Uses `bleak` library. Provides both sync (`scan()`) and async (`scan_async()`) variants. Automatically detects encrypted vs unencrypted protocol packets. Unencrypted protocol (version 1) packets carry a 34-bit network ID and up to 18 bytes of customer payload; `parse_unencrypted()` extracts these fields. AES-EAX protocol (version 2) packets carry a 2-byte nonce salt, 8-byte EID, encrypted payload (0-9 bytes), and 4-byte auth tag; `AesEaxPacket` stores these parsed fields plus `raw`, the service data byte for byte (the cloud decode endpoint needs it). For AES-CTR, `EncryptedPacket.payload` already is the whole advertisement. Unknown protocol versions (3+) are captured as `UnknownPacket`.

- **`ready.py`** - Hubble Ready device provisioning (UUID 0xFCA7). Handles GATT connections, characteristic reads/writes, and the full provisioning flow (register with backend, write key/config/time).

- **`crypto.py`** - Local packet decryption. Implements AES-CTR decryption with CMAC-based key derivation (SP800_108_Counter KDF). Supports both AES-256-CTR and AES-128-CTR. `decrypt()` accepts `counter_mode` as `"UNIX_TIME"` (default, UTC day-based) or `"DEVICE_UPTIME"` (counter-based, fixed pool size 128). Exports `UNIX_TIME` and `DEVICE_UPTIME` constants. `decrypt_eax()` decrypts AES-EAX packets by iterating counters 0-127, generating candidate EIDs via AES-ECB, and using `AES.MODE_EAX` for authenticated decryption. Uses key directly (no KDF). `decrypt_satellite()` decrypts a satellite packet's payload using the same AES-CTR/CMAC scheme as `decrypt()`; satellite packets deliver `seq_num`, `auth_tag`, and encrypted payload as separate fields (not packed into one advertisement). It accepts `counter_mode` (`"UNIX_TIME"` default, day-based; or `"DEVICE_UPTIME"`, sweeping the fixed 0-127 counter pool) just like `decrypt()`. `decrypt_at()` decrypts a CTR packet at one known counter. `ctr_eid()` computes the 4-byte EID a CTR device broadcasts for a counter, ported from hubble-device-sdk's `hubble_internal_device_id_get` and pinned to vectors from its `tools/ble-adv.py`; compare it to `adv[2:6]` (raw bytes, as the firmware memcpys them). `eax_eid_index()` is the EID-only half of `decrypt_eax()`, so "EID matches, tag fails" can be told apart from "wrong key".

- **`detect.py`** - Decryption-strategy auto-detection, decoupled from the CLI (imports no `click`, never prints). `CtrCounterModeDetector` and `EaxExponentDetector` are per-scan stateful objects that hold the detection cache and own the detect/sweep loop; their `decrypt()` takes a caller-supplied packet-bound `decrypt_fn` and returns a `Detection(result, label)` — `label` is set only on the first successful detection of a scan. The CLI builds the `decrypt_fn` (so test mocks of `cli.decrypt`/`cli.decrypt_eax` still apply) and prints the `[INFO] Detected:` line itself when `label` is set.

- **`validate.py`** - Key-setup diagnosis behind `ble validate`, decoupled from the CLI like `detect.py`. Evidence comes from the registration (`Device` from the single-device GET), the air (`AirScan`) and, optionally, the firmware build (`inspect_firmware()`). `diagnose()` cross-checks them into `Finding(check, status, summary, advice)` rows, which have the same shape as doctor's check tuples; `cli._CHECK_*` are aliases of `validate.OK/FAIL/SKIP`. Every setting goes through one `_crosscheck()` with one precedence (a build that disagrees with the registration is the cause, then the air, then a board not running the given build). The exception is air that conclusively agrees with the registration: then the build given is reported as not the one the board runs, so the advice never re-registers a working device (a DEVICE_UPTIME reading is not conclusive, since it is also an unset UNIX_TIME clock). `AirScan` is differential because the decrypt functions return None for every kind of failure. It groups packets by EID, so other devices in range are ignored. Its EID table (cached, built before the scan, not in the BLE callback) holds every EID the key could produce: UNIX_TIME days from a year back to 30 days ahead, day counters 0-365 (the DEVICE_UPTIME pool 0-127, and above it a UNIX_TIME clock started at the 1970 epoch, which can only be an unset clock), and the key's first 16 bytes for a 32-byte key, since a `CONFIG_HUBBLE_NETWORK_KEY_128` build reads only that much. It then verifies the tag. When no EID matches, it falls back to a tag sweep over ±2 days for up to 32 streams. A hit there is reported as its own failure ("carry the wrong EID"), not a pass, because the backend looks devices up by EID. `inspect_firmware()` reads the key size and counter source primarily from the HDCV string (`HDCV:1.0/E:128/CS:UT/...`, built by hubble-device-sdk's `src/utils/hdcv.h` and compiled into every image); `E:` means AES-CTR only with `TV:0` or no `TV`. That needs only the flashed file and works for any build system: the EM9305 reference app is plain CMake with `-imacros hubble_config.h` and has no Kconfig at all. `CONFIG_HUBBLE_*` from `.config`/`sdkconfig`/`autoconf.h` is the fallback, and is reported as stale when it disagrees with the image. It searches `.elf`/`.bin`/`.hex`/`.ihex` (stdlib Intel-HEX decode) for the key bytes, preferring images under `build*/` that carry an HDCV over a vendor SDK's prebuilt images. Tested in `tests/test_ble_validate.py`, together with the command.

- **`claim.py`** - `DeviceClaim` dataclass (a hand-off of devices from a source org to a destination org) plus `encode_claim_token()` and the `AVAILABLE`/`IN_PROGRESS`/`COMPLETED` constants. Wire facts verified against the cloud repo (`platform-api/api/device_claims.go`, not in the public `openapi.yaml`): endpoints are `/org/{id}/device_claims[/{claim_id}[/claim]]` (the `/api` prefix already means `/v1`, so never add `/v1`); list paginates via the `Continuation-Token` header and takes `role=source|destination` and `filter_status`; claim PATCH fields are `set_destination_org_id`/`set_claim_token`/`set_name` with `""` clearing (null is ignored); a token is looked up only by GET, as **unpadded** base64url with `id_type=claim_token`, and redeem/PATCH/DELETE take only a literal `claim_id`; `device_count` comes only from the single GET, which lists `devices` only when exactly one is linked; no device endpoint returns a device's `claim_id` or `activated`. `new_claim_using_device_id` mints a claim whose ID is the device ID. `set_activated` must be the only field in its PATCH. Entitlements: `can_create_device_claims` (create/link/provision-with-claim) and `can_deactivate_devices` (`activated: false`); redeem needs none. Error bodies carry the message in `description`, which `raise_for_response` reads; 409 maps to `ConflictError`. `Organization` gains `create_claim`, `iter_claims`/`list_claims`, `get_claim`, `update_claim`, `delete_claim`, `link_device`/`unlink_device`, `link_devices`/`unlink_devices` (one `PATCH /org/{id}/devices` per `cloud.BATCH_UPDATE_LIMIT`=1000; the cloud checks a batch before writing it, so a missing device 400s the whole batch naming only that device, and `claim link`/`unlink` drop it and resend the rest), `redeem_claim` (polls to COMPLETED), `register_devices` (n devices, `claim_id=`/`new_claim=`, `activated=`; `register_device` delegates to it; sent in requests of `cloud.REGISTER_BATCH_LIMIT`=1000, the cloud's `n_devices` max, and a failure after the first request raises `PartialRegistrationError` carrying the devices and keys already registered, which the CLI prints before the error) and `set_device_activated`.

- **`packets.py`** - Data classes: `Location`, `EncryptedPacket`, `DecryptedPacket`, `AesEaxPacket`, `UnknownPacket`.

- **`device.py`** - `Device` dataclass representing a registered device. `encryption`, `counter_source`, `period_exponent` and `last_packet_ts` are filled only by the single-device GET (`Organization.get_device()`); the list endpoint omits the registration config.

- **`errors.py`** - Exception hierarchy. Base `HubbleError` with specialized errors for backend, network, validation, BLE scanning, and decryption failures. HTTP 403/404/429 map to `PermissionDeniedError`/`NotFoundError`/`RateLimitError` (all `BackendError` subclasses); `raise_for_response` clips oversized error bodies to 300 chars for every endpoint.

- **`cli.py`** - Click-based CLI. Command groups: `ble` (scan, decode, validate), `claim` (list, get, create, update, delete, link, unlink, redeem, register-device, activate, deactivate; tests in `tests/test_claims.py`; `redeem` GETs the claim first, previews it on stderr and asks via `_ask_yes_no()` (not `click.confirm`, which writes a byte to stdout and can't tell EOF from Ctrl-C), `--yes` skipping; IN_PROGRESS for this org rejoins without asking, COMPLETED into this org is a no-op), `ready` (scan, info, read-status, read-key-info, read-config, read-time, write-key, write-config, write-time, provision), `org` (info, list-devices, get-packets, register-device, delete-device, set-device-name), `sat` (scan, mock-scan, record, signal-report; `scan` accepts `--key`/`--days`/`--counter-mode`/`--show-failed-decryption` to decrypt payloads locally — when `--key` is given without `--counter-mode`, the counter source is auto-detected (UNIX_TIME vs DEVICE_UPTIME) and announced, mirroring `ble scan`. `record DURATION` captures raw IQ samples to a `.npy` file (container `/api/iq_capture`); `signal-report DURATION` records IQ then re-analyzes it offline into a plain-text RF signal-diagnostic report — per-symbol timing/drift, channel-hopping validation, amplitude/SNR, chipset metrics; **no packet payloads** (container `/api/record_analyze`). Both take `--output`/`--mock`/`--pluto-uri`/`--debug` and are one-shot — they start the receiver, make a single blocking request, and exit. `scan` polls the live `/api/packets` feed instead). Top-level: `doctor`, `validate-credentials`.

- **Scan output contract (`ble scan`, `ble decode`, `sat scan`)** - Tabular output is one line per packet: `TIME`, `RSSI` plus a 5-cell signal bar (`_signal_bar()`, bar length carries magnitude), `V`, `EID`/`NET_ID`, `CTR/SEQ`, `PAYLOAD`, with a `✓`/`✗` decrypt mark in the gutter under `--show-failed-decryption`. Forensic columns sit behind `--debug` (`EPOCH`, `TAG`, `SALT` for BLE; `RS_CORR`, `SYM_MS`, `GAP_MS` for satellite). Three rules hold: packet rows are the only thing on **stdout** and all chrome (scanning notice, detection lines, summary via `_scan_summary()`) goes to **stderr**; `-o json` is byte-stable, so the tabular-only `auto` payload default is resolved by `_effective_payload_format()` rather than by changing the Click default; and cells truncate through `_fit()`, which appends the real byte count (`+18B`) so a row never outgrows its rule. When failures are hidden the summary tally reads `N decrypted` (never `0 failed`) and a separate line counts the hidden ones. `ble decode` uses its own column set (`_DecodeTablePrinter`: `TIME`, `RSSI`+bar, `DEVICE`, `SEQ`, `CTR`, `PAYLOAD`) under the same rules; an undecrypted row shows `eid:<hex>` as DEVICE and its ciphertext always as hex, whatever `--payload-format` says. Its JSON (`_decoded_to_dict`, decode-only) gives decoded and failed rows the same keys (`sequence`, `counter`, `device_id`, `device_name`, `tags`, null when unknown); `ble scan` JSON keeps `seq_no`. Tests in `tests/test_cli_scan_display.py` and `tests/test_cli_ble_decode.py` lock all of this.

- **Org output contract (`org info`, `org list-devices`, `org get-packets`)** - Same column system, streamed through `Organization.iter_devices()` / `iter_packets()` rather than buffered, so the first rows land in ~1.6s instead of after a 15s silent fetch. `_OrgTablePrinter` renders rows, `_FetchProgress` reports page-by-page progress on stderr once the wait passes ~1s, and `_org_heading()` / `_org_summary()` keep all chrome on stderr. `--limit` defaults to off and always declares how a run stopped. `-o json` and `-o csv` still buffer, so their bytes are unchanged; the tabular-only `auto` payload default goes through `_effective_payload_format()`. `pass_orgcfg` resolves a `_LazyOrg` inside the command body, so `org <sub> --help` no longer needs credentials. Tests in `tests/test_cli_org_display.py` lock all of this.

- **`termcaps.py`** - The only module in the package allowed to contain non-ASCII, enforced by `tests/test_terminal_compat.py::TestSourceStaysAscii` (ruff can't do this: RUF001-003 only flag *confusable* characters, so box-drawing sails through). Holds two `Glyphs` instances, `UNICODE` and `ASCII`, whose every field must have identical `len()` so the fixed-width tables keep their arithmetic. `ascii_mode()` resolves `--ascii/--no-ascii` > `HUBBLE_ASCII` > an encoding probe derived from the glyph set itself (not a codec denylist, which is why `latin-1` is correctly rejected: it encodes `·` but not `─`). `color_enabled()`/`force_color()` implement `NO_COLOR`/`FORCE_COLOR`, which **Click does not support at any version**. Colour is applied in the *root group callback* because Click copies `color` from parent to child when a context is constructed, so setting it later reaches nothing.

- **`doctor`** - `hubblenetwork doctor` is the setup validation step: credentials (present, and valid via `cloud.get_env_from_credentials`), Bluetooth, Docker, and the cached receiver image. Exits 1 if any check FAILS; SKIP never fails a run. The Bluetooth check is deliberately **static** (`_bluetooth_usage_description()` reads the interpreter's `Info.plist` looking for `NSBluetoothAlwaysUsageDescription`) because touching CoreBluetooth without that key is what aborts the process, so a probing check would be the crash it is meant to report. Tests in `tests/test_cli_doctor.py`.

- **`ble validate`** - `hubblenetwork ble validate [--key <key>] [--device-id <id>] [--firmware]` checks one device end to end and names what is wrong. It replaced the old `ble validate` (a stop-at-first-failure walk ending in an ingest round trip), `ble check-time` and `ble detect`, and folds in PR #58's key-free cloud check. Existing `ble validate --key K --device-id D` invocations keep working. At least one of `--key`/`--device-id` is required (a usage error otherwise). `--key` alone covers the old `ble check-time`: no credentials, a SKIP Registration row, and the air, counter mode and Clock rows. `--device-id` adds the Credentials, Registration and Backend rows; it must be a UUID, since it goes into the URL path. `--device-id` alone needs no key: the scan runs in `_CLOUD_SCAN_WINDOW_S` (5s) windows, sending everything heard (`_Heard`, one packet per EID, so the cap of 100 counts devices, not advertisements) to the cloud after each, and stops once a packet decodes as this device; the Over the air row then only counts packets heard. A run where every row is a SKIP (e.g. `--timeout 0` without `--device-id`) prints "Nothing was checked." and exits 1. `--firmware` is optional, and rows it can't fill are omitted or SKIPped rather than failed; without `--key` it reads only the build config. The air row counts only this key's packets, never other devices in range. Mismatches are named directly. A build that disagrees with the registration is reported as the cause ahead of what the air shows. When the build *agrees* on UNIX_TIME, a counter in the 0-127 uptime pool is re-read as a Unix clock that was never set (Clock row: "device clock reads 1970-02-12"), since the two are cryptographically identical and only the build breaks the tie. Other mismatches: registered UNIX_TIME but broadcasting DEVICE_UPTIME; an AES-128 build reading 16 bytes of a 32-byte key; a `--key` length that disagrees with the registration; a clock outside ±2 days; an EAX period mismatch. The Backend row comes from `_CloudCheck`, which sends packets heard to `org.decode_packets` and builds `validate.CloudEvidence`. With `--key`, only this key's authenticated packets (`AirEvidence.packets`, up to 25) are sent: decoded as this device passes; decoded as another device fails as a key registered to another device; undecoded fails as "the registered key is not this --key". If `--key` opened nothing, everything heard is sent, and a decode as this device adds a "Key" FAIL row (the device is in range under another key). Decoding stores the packets, so this machine is the gateway and no Delivery row is added. When the token lacks `read-packets` (403) or the request fails, the Backend row falls back to `most_recent_packet` under 10 minutes old (fixed; no option), since an older packet may predate the reflash or key change being diagnosed, with a line saying why; "Delivery" then fires when the key setup is right but the backend has nothing, pointing at `ble scan --key <key> --ingest`. Agreement rows appear only when two or more sources were compared. With a key, the scan is `ble.scan(timeout, until=...)`: `validate.AirScan` analyses packets as they arrive and returns True once this key's packet authenticates, so `--timeout` is an upper bound and a nearby device answers in a second or two. `--timeout 0` skips the scan. There is no JSON output, `--within` or `--ingest`; all were removed deliberately. The removed `ble detect` / `ble check-time` names give a usage error pointing at `ble validate` (`cli._REPLACED_COMMANDS`). It is the only key-checking command, so there is one sweep to maintain. `detect.py` keeps only the per-scan detectors that `ble scan`/`sat scan` use to decrypt a stream. On macOS it checks `_doctor_bluetooth()` before scanning rather than crash. It shares doctor's rendering via `_check_marks()` / `_print_check()` / `_print_check_footer()`, and exits 1 on any FAIL. The scanning notice goes to stderr. Tests in `tests/test_ble_validate.py`.

- **Help and error-recovery contract** - Every group uses `cls=HubbleGroup`, which (a) renders help as a table of real invocations built from the Click tree via `_walk_commands()` / `_invocation()`, so a new command cannot go undocumented, and (b) overrides `resolve_command` to search the *whole* tree on an unknown name — Click only checks siblings, so from the root it can't see that `list-devices` lives under `org`. Ordering and blurbs come from `_GROUP_ORDER` / `_GROUP_BLURB`; the four examples come from `_START_HERE`; `_HELP_COL = 35` keeps the widest row inside 80. Every command carries a plain-language `short_help=` (asserted present and ≤44 chars for all 37). Required arguments use `cls=GuidedArgument` with a `metavar` (`<id>`, `<seconds>`) and `guidance` naming how to find the value. `_credentials_error()` distinguishes not-set from rejected; `_get_env_or_fail()` names the export. `main()` handles `UsageError` separately so the usage preamble survives, a message that is already a usage block gets no `Error:` prefix, and an unrecognised option gets the command's accepted option list appended. `validate-credentials` exits 1 on failure (it used to exit 0, making failure undetectable in scripts). Tests in `tests/test_cli_help_and_errors.py` lock all of this, including `TestReadmeStaysTrue`, which resolves every `hubblenetwork ...` line in `README.md` **and `plugins/**/*.md`** through the real Click tree (84 invocations today). It reads only shell-tagged fences, so illustrative error output in a bare fence is not treated as a runnable example. The plugin skill docs had drifted to documenting `--pool-size` and `ready provision --format json`, neither of which exist, precisely because nothing checked them.

- **`sat.py`** - Satellite packet scanning via PlutoSDR. Manages Docker container lifecycle (pull, start, stop) and polls the container's HTTP API for decoded packets. Requires Docker daemon running. Image: `ghcr.io/hubblenetwork/sdr-docker:latest`. For real (non-mock) scans, after the receiver API is up `scan()` calls `_wait_for_sdr()`, which polls the container's `/api/status` `sdr_connected` field and raises `SatelliteError("No PlutoSDR detected …")` if the SDR never connects within the grace period — so a missing/unplugged Pluto fails fast instead of silently yielding nothing. The check is skipped for older receiver images that don't report `sdr_connected`.

### Key Patterns

- **Sync/Async duality**: BLE and provisioning functions have both sync and async variants. Sync versions use `asyncio.run()` with fallback handling for existing event loops.

- **Environment auto-detection**: `get_env_from_credentials()` tries PROD then TESTING to determine which API the credentials are valid for.

- **Pagination**: Cloud API uses continuation tokens. `Organization.list_devices()` and `retrieve_packets()` handle pagination internally.

- **Fake packets for tests**: `tests/fake_packets.py` builds correctly encrypted raw advertisements (`make_ctr` for AES-CTR UNIX_TIME/DEVICE_UPTIME, with its EID from `crypto.ctr_eid`; `make_eax` for AES-EAX) and `as_packet()` parses them through the real BLE parser. Round-tripped against `crypto.decrypt`/`decrypt_eax` in `tests/test_cloud_decode.py`.

- **Encryption modes**: Devices support either AES-256-CTR (32-byte key) or AES-128-CTR (16-byte key). Mode is auto-detected from device during provisioning.

- **EID modes**: Two EID rotation modes — UNIX_TIME and DEVICE_UPTIME. Device-uptime mode uses a fixed pool size of 128. The `decrypt()` function's `counter_mode` parameter accepts `"UNIX_TIME"` (default) or `"DEVICE_UPTIME"`; CLI commands use `--counter-mode UNIX_TIME|DEVICE_UPTIME`. For AES-128-EAX device registration on DEVICE_UPTIME, the rotation period can be set via `period_seconds` (SDK) / `--period-seconds` (CLI) or `period_exponent` / `--period-exponent` (period = 2^n seconds; cloud accepts 10-15, default 15 ≈ 9h). The two are mutually exclusive.

- **Satellite scanning requires Docker**: `sat.scan()` pulls and runs a privileged Docker container. Docker daemon must be running. Raises `DockerError` (not `SatelliteError`) if Docker is unavailable. The `docker` Python package is a required (not optional) dependency.

### Releasing
Use the `/release` skill to cut a release. It bumps the version in `pyproject.toml`, generates release notes from conventional commits into `release-notes.md`, commits, tags (`vX.Y.Z`), and pushes. The tag push triggers `.github/workflows/release.yml` which runs tests, builds, creates a GitHub Release, and publishes to PyPI via trusted publishing.

### Conventions
- **Commit messages**: Use conventional commits — `feat(scope):`, `fix(scope):`, `docs:`, `test(scope):`, `chore:`. The scope is typically the module name (cli, org, ble, ready, sat, crypto).

### Test Markers
- `@pytest.mark.integration` - Tests requiring real API credentials
- `@pytest.mark.ble` - Tests requiring BLE hardware
